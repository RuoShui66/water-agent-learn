# Common workflow patterns for AI agents—and when to use them：面试速记

> 2026-03-05 · [官方原文](https://claude.com/blog/common-workflow-patterns-for-ai-agents-and-when-to-use-them)
> 可视作 `02_building-effective-agents`（2024-12）的 2026 版重写——同样的问题，更收敛的答案。

## 一句话讲明白

**工作流（workflow）不是多智能体（multi-agent）。工作流是「流程编排」——三种基本形状：串行、并行、评估–优化循环。官方的态度比 2024 年那篇更保守：先试单 Agent，只有在能测出改进时才引入工作流。「因为能并行就并行」是反模式。**

## 为什么值得读 / 能用在哪

- **它和 [B18 五种协调模式](B18_multi-agent-coordination-patterns_学习笔记.md) 是两个层次，别混**：本文讲**流程形状**（怎么排），B18 讲**信息流动架构**（怎么连）。面试时能区分这两层，说明你读得细。
- 三种模式极简，五分钟能记住，但**每种的代价（latency / cost / token）说得很清楚**，是回答「取舍」类问题的好素材。
- 「先单 Agent，能测出改进再加」这条克制的原则，比堆架构更能体现工程判断力。

## 核心要点

### 三种工作流模式

```
1. Sequential   串行
   [A] → [B] → [C]        每步等上一步

2. Parallel     并行（fan-out / fan-in）
        ┌→ [A] ─┐
   in ──┼→ [B] ─┼→ 聚合 → out
        └→ [C] ─┘

3. Evaluator-Optimizer  评估–优化
   [生成] → [评估] → 反馈 ─┐
      ↑───────────────────┘   循环至达标
```

---

### 1. Sequential Workflows（串行工作流）

**定义**：按预定顺序执行，线性数据流。每个 Agent 处理输入，把结果传给下一环。

| | |
|---|---|
| **适用** | 有明确依赖的多阶段流程；数据转换流水线；**草稿–评审–润色**这类循环 |
| ⚠️ **代价** | **增加延迟**——每一步都要等上一步 |
| ✅ **收益** | **让每个 Agent 只专注一件事，能提升准确度** |

> 「让每个 Agent 只专注一件事」是串行的真正价值，不是「因为流程本来就是顺序的」。如果拆开之后每个 Agent 的任务并没有变简单，串行就只是白白加延迟。

### 2. Parallel Workflows（并行工作流）

**定义**：把独立任务分发给多个 Agent 同时执行，用 **fan-out / fan-in** 模式。

| | |
|---|---|
| **适用** | 独立子任务；**多维度评估**；代码审查；文档分析 |
| ⚠️ **代价** | **并发 API 调用更贵**；**需要聚合策略**（结果怎么合） |
| ✅ **收益** | 更快完成；关注点分离 |

⭐ **官方明确的反模式**：
> 不要因为**能**并行就并行——只在并发执行有清晰收益时才加。

**「需要聚合策略」这条容易被忽略**：并行的难点通常不在扇出，在扇入——三个 Agent 给了三个互相冲突的结论，谁来裁决？这个问题不解决，并行就是把复杂度推到下游。

### 3. Evaluator-Optimizer Workflows（评估–优化工作流）

**定义**：生成 Agent 和评估 Agent 配对，评估器按标准打分并给反馈，生成器据此改进，迭代循环。

| | |
|---|---|
| **适用** | **质量标准清晰可测**：技术文档、客户沟通、有明确规范的代码生成 |
| ⚠️ **代价** | **token 用量成倍增长**；**增加迭代时间** |
| ✅ **收益** | 通过结构化反馈循环产出更好的结果 |

> 这个模式和 [B18](B18_multi-agent-coordination-patterns_学习笔记.md) 的 **Generator-Verifier** 是同一件事的两个视角：本文强调它是**流程形状**，B18 强调它是**协调架构**且验证器标准含糊时会给虚假安全感。`21_harness-design-long-running-apps` 里那套 planner/generator/evaluator 是它的完整落地。

---

### ⭐ 官方决策框架（本文最该记的部分）

> **先简单起步：优先试单 Agent 方案。只有当工作流能带来「可测量的改进」时才采用它。**

翻译成面试语言：

1. **默认单 Agent** —— 工作流是要论证的，不是默认的
2. **判据是「可测量」** —— 不是「感觉更清晰」「架构更漂亮」
3. **每种模式都有明确代价** —— 串行加延迟、并行加成本、评估–优化加 token 和时间

这条克制原则和 `02_building-effective-agents` 里那句「找到最简单的解，只在需要时才增加复杂度」是一脉相承的，只是 2026 年说得更具体了：**给出了「可测量改进」这个可执行的判据**。

## 术语中英对照

| 英文 | 中文 | 说明 |
|---|---|---|
| workflow | 工作流 | 流程编排，区别于 multi-agent 架构 |
| sequential workflow | 串行工作流 | 线性依赖，每步等上一步 |
| parallel workflow | 并行工作流 | 独立任务同时执行 |
| fan-out / fan-in | 扇出 / 扇入 | 分发与聚合 |
| evaluator-optimizer | 评估–优化 | 生成与评判配对迭代 |
| aggregation strategy | 聚合策略 | 并行结果怎么合并/裁决 |

## 三种模式代价速查

| 模式 | 主要代价 | 什么时候值 |
|---|---|---|
| 串行 | **延迟** | 拆开后每个 Agent 的任务确实变简单了 |
| 并行 | **成本** + 需要聚合策略 | 子任务真正独立，且并发有清晰收益 |
| 评估–优化 | **token 成倍** + 迭代时间 | 质量标准清晰可测 |

## 面试怎么用

**被问「workflow 和 multi-agent 有什么区别」**（很好的区分度问题）：
workflow 是**流程形状**——三种：串行、并行、评估–优化，回答的是「步骤怎么排」；multi-agent coordination 是**信息流动架构**——五种（编排者–子智能体、智能体团队、消息总线、共享状态、生成器–验证器），回答的是「Agent 之间怎么通信」。一个系统可以是「并行的工作流」跑在「智能体团队」架构上。

**被问「你会怎么选架构」**：
先给官方原则——**默认单 Agent，只有能测出改进才上工作流**；然后按代价来选：串行付延迟、并行付成本、评估–优化付 token。最后补那句反模式：「不要因为能并行就并行。」

**加分点**：主动指出并行的真正难点在**扇入**（聚合策略）而不是扇出——三个 Agent 给出冲突结论时谁裁决，这个问题不解决就只是把复杂度推给下游。
