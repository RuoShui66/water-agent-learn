# The new rules of context engineering for Claude 5 generation models：面试速记

> 2026-07-24 · [官方原文](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)
> ⚠️ **这篇直接更新了 Engineering 卷的 `10_effective-context-engineering-for-ai-agents`（2025-09）。那篇的若干结论在 Claude 5 世代已经反转。**

## 一句话讲明白

**Anthropic 把 Claude Code 的系统提示词删掉了 80% 以上，性能没有下降。结论很扎心：过去那套「给规则、给示例、把信息一次性喂满」的上下文工程，在更强的模型上不是帮助，而是束缚——因为你写的每条规则，都是在用你的判断力覆盖一个判断力已经比你好的模型。**

## 为什么值得读 / 能用在哪

- **这是全套 Anthropic 上下文工程材料里唯一一篇「推翻前作」的**。面试时如果你还在背 2025 年那套「要给详细示例、要重复关键指令」，会显得知识过期。
- 80% 这个数字本身就是最好的论据：不是理论推演，是拿生产系统实测出来的。
- 它给了一张**新旧做法对照表**，可以直接背，是极高性价比的面试弹药。
- 「progressive disclosure（渐进披露）」在这里被确立为**默认策略**，而不是可选优化。

## 核心要点

### 1. Unhobbling：核心概念

原文用了 **unhobbling（解除束缚）** 这个词——把强加在模型身上的限制拿掉。这个词选得很准：它把「提示词工程」重新定义成了**减法**而不是加法。

**Anthropic 的实测**：为 Claude 5 世代高级模型删掉 Claude Code 系统提示词的 **80%+**，性能无损失。

**推论**：如果你的提示词里那 80% 是无用功，说明你在为一个不存在的能力缺口买单。而这个缺口是随模型版本移动的——每次模型升级，都该回头问「哪些约束现在可以删了」。

> 这跟 `21_harness-design-long-running-apps` 里「新模型上线后该拆掉哪些脚手架、一次只拆一个」是**完全同构**的动作，只是一个作用在 harness 上，一个作用在提示词上。**面试时把这两条并起来讲，会显得你抓到了 Anthropic 的元方法论：harness 和 prompt 都是模型能力缺口的补丁，缺口会移动，补丁要定期回收。**

### 2. ⭐ 新旧做法对照表（本文最核心的产出，建议背下来）

| 过去的做法 | 现在的做法 | 为什么变 |
|---|---|---|
| 给 Claude 明确的规则 | **让 Claude 自己判断** | 规则是在用你的判断覆盖模型的判断 |
| 提供工具使用示例 | **把工具接口设计得更好** | 接口本身应该自解释，示例是接口设计失败的补丁 |
| 上下文一次性全给 | **渐进披露（progressive disclosure）** | 一次性喂满会稀释注意力 |
| 关键指令全文重复 | **只写在工具描述里** | 重复会制造指令冲突 |
| 在 CLAUDE.md 里手工维护记忆 | **自动的上下文记忆** | 手工维护跟不上 |
| 简单 markdown 规格 | **富引用：代码、HTML、测试套件** | 代码比描述精确得多 |

### 3. 四层上下文各自该怎么写

原文按「上下文组装」的层次给了分层建议：**System Prompt → CLAUDE.md → Skills → References**。

| 层 | 该放什么 | 不该放什么 |
|---|---|---|
| **System Prompt** | 保持轻量、只放产品特有的东西 | 用 Claude Code 就别改它；自建 Agent 才值得在这层花力气 |
| **CLAUDE.md** | **仓库特有的坑（gotchas）** | 显而易见的信息；冗长的指导（改成引用 Skill） |
| **Skills** | 团队特有的观点与最佳实践；用多文件结构做渐进披露 | 过度约束——除了关键领域 |
| **References** | 用 `@mention` 指向规格、设计稿、代码库 | 用文字描述代替代码——**能给代码就别给描述** |

> **「仓库特有的坑」这个筛选标准非常实用**。判断某条内容该不该进 CLAUDE.md，只问一句：**这件事模型自己猜得到吗？** 猜得到就删。

### 4. 指令冲突：一个被低估的失败模式

原文有一张图专门画**重叠的系统指令互相冲突**。这是「重复关键指令」这条旧做法的直接代价——你在三个地方写了三份措辞略有差异的同一条规则，模型要花注意力去调和它们。

**这条在面试里很好用**：被问「上下文越多越好吗」，答案不是笼统的「会稀释注意力」，而是具体的**指令冲突**——多份措辞不一致的规则会互相打架，模型的处理成本比没有规则还高。

### 5. 工具设计取代示例

原文举的例子是 **Todo 工具的 status 参数枚举**：与其写一段示例教模型什么时候该标记完成，不如把 status 设计成一个清晰的枚举，让接口自解释。

**核心转换**：从「教模型怎么用工具」变成「把工具做得不需要教」。这跟 `08_writing-tools-for-agents` 是一脉相承的，但态度更激进——示例被明确定性为**接口设计失败的补偿**。

### 6. 新工具：`claude doctor`

原文提到一个新命令 `claude doctor`，用来**自动给 skills 和 CLAUDE.md 做「合身化」（rightsize）**——即自动检测哪些内容该删。

> 这是 unhobbling 从方法论落到工具的证据：Anthropic 认为「定期删提示词」是个应该被自动化的常规动作，而不是偶尔的清理。

### 7. 一个能体现新风格的写法

原文举了个例子说明「判断式指导」长什么样——大意是让写出的代码读起来像周围的代码：注释密度、命名、惯用法都对齐。

对比一下就明白差别了：
- **旧写法**：列一张规则表——变量用 camelCase、每个函数必须有 docstring、行宽不超过 100……
- **新写法**：一句「匹配周围代码的风格」。

后者把**判断权交回模型**，而且天然适应任何代码库，不需要为每个项目重写规则表。

## ⚠️ 旧文章中需要修正的结论

| `10_effective-context-engineering` 中的结论 | Claude 5 世代的修正 |
|---|---|
| 给足够的示例帮助模型理解工具 | 改为把工具接口设计好；示例是接口失败的补丁 |
| 在关键位置重复重要指令 | 反了——会造成指令冲突，只写在工具描述里 |
| 前置组织好完整上下文 | 改为渐进披露 |
| 用 markdown 写清楚规格 | 优先给代码 / HTML / 测试套件等富引用 |
| 精心维护 CLAUDE.md | 只留仓库特有的坑，其余交给自动记忆与 Skills |

## 面试怎么用

**被问「上下文工程怎么做」**：
不要背 2025 年那套。先给对照表的核心转向——**从加法到减法**，然后甩数据：Anthropic 删掉 Claude Code 系统提示词 80%+ 性能无损。再补方法论：每次模型升级都要回头问「哪些约束可以拆了」，跟 harness 做减法是同一个动作。

**被问「你怎么组织项目的 AI 上下文」**：
按四层答（System Prompt / CLAUDE.md / Skills / References），每层给筛选标准，重点强调 CLAUDE.md 的判断法则——「模型自己猜得到的就删」。

**加分点**：主动指出这篇推翻了 Anthropic 自己 2025 年的建议，并说明为什么（模型判断力超过了写规则的人）。这显示你在跟踪演进而不是背静态知识。
