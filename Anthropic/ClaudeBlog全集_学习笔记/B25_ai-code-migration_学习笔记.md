# How Anthropic runs large-scale code migrations with Claude Code：面试速记

> 2026-07-16 · [官方原文](https://claude.com/blog/ai-code-migration)
> **全套材料里数字最硬、工程细节最实的一篇。**长任务 Agent 系统的完整生产落地范本。

## 一句话讲明白

**Bun 的一百万行代码从 Zig 迁到 Rust，用了不到两周、约 16.5 万美元 token 成本；Mike Krieger 一个周末把 16.5 万行 Python 迁成 TypeScript。方法论只有一句话——你修的不是代码，是产出这些代码的循环（loop）。审查者抓到重复错误时，修复不是逐文件改，而是往规则手册里加一句话，然后重新生成受影响的整批文件。**

## 为什么值得读 / 能用在哪

- **这是「长任务 Agent 到底能干多大的活」最有说服力的一手证据**，带完整成本、性能、缺陷数字。
- 六步流程可以**整套搬到任何批量改造场景**（不只是语言迁移：框架升级、API 迁移、测试补齐）。
- 「修循环不修代码」这句话是**整套 Agent 工程思维的浓缩**，面试里单独拎出来讲都够了。
- 「人力前置」「验证机械化、审查对抗化」「队列可恢复」这三条，是把 Agent 从 demo 推到生产的关键。

## 一、经济账为什么变了

| | 过去 | 现在 |
|---|---|---|
| 语言迁移成本 | **300–400 万美元 / 4 年** | 几万到几十万美元的 token |
| 立项门槛 | 需要**生存级威胁**才批 | **长期瓶颈或性能问题**就够了 |

**Bun 迁移实际花费：约 165,000 美元 token 成本。**
Mike 的项目收益：编译时间从 **8 分钟 → 2 秒**。

### 为什么 AI 特别适合迁移（五个结构性原因）

1. **可大规模并行** —— 数千个互相独立的文件
2. **规格明确** —— **原代码本身就是参考答案**
3. **验证内建** —— 现成的测试套件
4. **工作队列自我生成** —— 编译错误和测试失败**自动产生下一批任务**
5. **一致性强制** —— 防止悄悄发散

> **第 2 和第 4 条是关键**。迁移是罕见的「规格完备 + 验证免费 + 任务自生成」任务，所以它是 Agent 的最佳战场。**面试被问「什么任务适合交给 Agent」，按这五条答**，比说「重复性劳动」有深度得多。

## 二、⭐ 六步流程

### Step 1：规则手册 + 依赖图 + 缺口清单

| 产物 | 作用 |
|---|---|
| **规则手册（Rulebook）** | 编码翻译策略与架构决策。**结构保留型迁移**（Zig→Rust）就是类型和惯用法映射；**重新设计型**（Python→TS）它就变成一份设计文档 |
| **依赖图（Dependency Map）** | 用**确定性脚本**（不是模型）识别文件关系，从而切出并行工作流。C/C++、Python 这类没有正式清单的语言必须显式建图 |
| **缺口清单（Gap Inventory）** | 编目「新语言要求显式表达、但旧语言是隐式的」知识 |

**缺口清单的例子**：Python 的鸭子类型接受任何有对应方法的对象；TypeScript 要求正式的 interface 契约，声明确切的结构和返回类型。这类差异不提前编目，就会在几千个文件里各自即兴发挥。

Jarred 还**按直觉预判常见错误类别，造了 8 个专精审查 Agent**。

### Step 2：压力测试规则

**用 3 个文件做迷你迁移**，在全面铺开前验证规则手册。

Jarred 的做法很妙：**跑两路并行翻译**——一路严格照规则手册，一路按资深工程师直觉，然后**对比 diff** 来修订规则。

> **这一步抓出了 2 个关键问题，避免了后续数千个级联问题。** 这是全文投入产出比最高的动作。

⚠️ **限制条件**：只对**结构保留型**迁移有效（翻译结果可逐行对比）。重新设计型项目改用**对设计文档做对抗式审查**。

### Step 3：翻译一切

**多 Agent 循环架构**：实现者（implementer）翻译 → 审查者（reviewer）评估 → 修复者（fixer）处理问题。

| 设计 | 说明 |
|---|---|
| ⭐ **模型分层策略** | **小模型（Sonnet）跑高吞吐的实现扇出；大模型负责审查和写规则给别人follow** |
| **队列机制** | 完成状态**机械判定**——翻译后的文件在磁盘上存在或不存在。批处理从磁盘状态恢复，**迁移天生可恢复** |
| **允许过度保守** | 这一步翻译保守没关系，编译器下一步会抓出来。标记为 `// TODO(port): <原因>` 的东西自动进入下一个队列 |
| ⭐ **对抗式审查** | **两个审查者独立评估**实现者的工作，**分歧升级给第三个 Agent** |

⭐⭐ **全文最重要的一句**：
> 审查者抓到**重复出现**的错误时，修复**不是逐文件改**——而是**往规则手册里加一句话，然后重新生成受影响的批次**。

**这就是「修循环不修代码」的具体形态。** 记住这个动作，它是把 Agent 工程和手工 Agent 使用区分开的分水岭。

### Step 4：编译

**编译放在哪取决于语言和编译耗时**：
- Mike：TypeScript 编译放在**每个循环内部**（秒级）
- Jarred：Rust 编译**推迟**以压缩循环时间，最后在整个工作区跑一次，由修复 Agent **并行处理错误**

**系统性问题在错误审查时浮现**：Jarred 修完 Zig 容忍而 Rust 不容忍的循环导入后，遇到数千个模块错误。他的解法不是逐个修，而是**编码一套逻辑把依赖分类为「删除 / 移动 / 重构」，然后全库应用**。

### Step 5：冒烟测试

测试执行产生的崩溃，**像编译错误一样机械地进入队列**。由对抗式 Agent 做**根因归类**，避免重复修复。

### Step 6：行为对齐

**分片执行测试**，与原代码库对比行为。失败在多个测试间重复出现时，**修订上移到规则层**——只重新生成被修订规则触及的文件。

⭐ **没有测试套件怎么办**：**先造一个。**
- Mike 造了一个**七场景对等性测试框架**（parity harness），对比 TypeScript 输出与 Python 原版
- 更进一步：**让 Claude 设计一套自主的端到端测试套件，通宵跑了四轮迭代**，抓到了任何手工场景列表都预测不到的边缘 case

## 三、⭐ 六条最佳实践（官方总结，建议背下来）

1. **不要盲目照搬** —— 每个迁移都不同，先和 Claude 一起做针对性规划
2. **关注模式，不是单个失败** —— 单点失败交给循环自动处理
3. ⭐ **审查要对抗化，验证要机械化** —— 脚本（编译器、diff、测试套件）当裁判
4. **策略性优化 token 花费** —— 小模型跑高吞吐，大模型写规则和审查
5. ⭐ **人力前置** —— 规则手册和压力测试消耗大部分人力时间，**之后全是队列燃尽**
6. **队列机械且可恢复** —— **「完成」的定义是产物在磁盘上存在**

> 第 3 条和第 6 条最值得单独记：
> - **「审查对抗化、验证机械化」** 精确区分了两种质量手段——主观判断用多 Agent 对抗（两个审查者 + 第三方仲裁），客观判断用确定性脚本。这跟 [B05](B05_building-agents-with-the-claude-agent-sdk_学习笔记.md) 「能确定性验证就别用 LLM-as-judge」是同一原则的展开。
> - **「完成 = 磁盘上有产物」** 让整个系统天然可恢复、可中断、可重入。这是长任务 Agent 系统最容易被忽略的架构要求——**不要把进度记在 Agent 的上下文里，记在文件系统上**。

## 四、生产结果（面试弹药，数字很硬）

### Bun：Zig → Rust

| 指标 | 结果 |
|---|---|
| 规模 | **100 万行，< 2 周** |
| Token 成本 | **约 $165,000** |
| 合并前测试 | **现有测试套件 100% 通过** |
| 合并后回归 | **19 个**（全部已修） |
| 内存 | 2000 次构建基准：**6,745 MB → 609 MB** |
| 二进制体积 | Linux/Windows **减少 19%** |
| 性能 | 真实负载 **快 2–5%** |
| unsafe 代码 | **约 4%**（主要在 C/C++ 边界） |

### Mike Krieger：Python → TypeScript

| 指标 | 结果 |
|---|---|
| 规模 | **16.5 万行，一个周末** |
| 编译时间 | **8 分钟 → 2 秒** |
| 二进制启动 | **快 6 倍** |
| 附带收益 | 消除了独立的部署流水线 |

## 面试怎么用

**被问「长任务 Agent 系统怎么落地」**：
用这篇当案例。给六步流程 → 强调**人力前置**（规则手册 + 压力测试吃掉大部分人力，之后是队列燃尽）→ 给数字（100 万行 / 2 周 / $165k / 合并前测试 100% 通过 / 合并后仅 19 个回归）。

**被问「怎么保证 Agent 产出质量」**：
答「**审查对抗化，验证机械化**」——主观判断用两个独立审查者 + 第三方仲裁分歧，客观判断用编译器/diff/测试套件当裁判。再补 Outcomes 那套独立上下文评分器（见 [B20](B20_managed-agents-memory-and-new-features_学习笔记.md)）。

**被问「Agent 跑一半挂了怎么办」**：
答「**完成的定义是产物在磁盘上存在**」——进度不记在上下文里，记在文件系统上，所以队列天生可恢复、可重入。

**被问「什么任务适合交给 Agent」**：
按五个结构性原因答：可并行、规格明确（原代码即参考答案）、验证内建、任务队列自我生成、一致性可强制。

**最能体现思维层次的一句**（可以直接用）：
> 修的不是代码，是产出代码的循环。审查者抓到重复错误时，修复不是逐文件改，而是往规则手册加一句话，重新生成受影响的批次。
