# Multi-agent coordination patterns: Five approaches and when to use them：面试速记

> 2026-04-10 · [官方原文](https://claude.com/blog/multi-agent-coordination-patterns)
> 与 `06_multi-agent-research-system`（2025-06）互补：那篇是一个系统的深度复盘，这篇是**成体系的模式手册 + 选型决策树**。

## 一句话讲明白

**多智能体不是一种架构，是五种。它们的真正差别不在「有几个 Agent」，而在「信息怎么流动」——是走中心节点、走共享队列、走事件总线，还是走共享存储。选错模式的代价通常不是慢，而是「信息瓶颈」或「无限反应循环」这类结构性故障。官方给的起手式很明确：先上 orchestrator-subagent，遇到具体瓶颈再演进。**

## 为什么值得读 / 能用在哪

- **面试问「多 Agent 怎么设计」，这五种模式就是标准答案的骨架**。能说出五种并给出选型依据，比泛泛而谈「主从架构」强太多。
- 每种模式官方都给了**明确的弱点**，这些弱点是面试追问时的加分点——说得出缺点才证明你真用过。
- 文末的**两两对比决策**（何时从 A 演进到 B）是最实用的部分，可以直接映射到系统设计题。

## 核心要点

### 五种模式总览

```
1. Generator-Verifier      生成器–验证器      ← 质量把关
   [生成] ⇄ [验证]  反馈直到通过或达迭代上限

2. Orchestrator-Subagent   编排者–子智能体    ← 默认起点
   [主] → 派发 → [子][子][子] → 汇总（子做完即终止）

3. Agent Teams             智能体团队        ← 并行长任务
   [协调者] → 启动 → [常驻工人][常驻工人] ⇄ 共享任务队列（工人保留上下文）

4. Message Bus             消息总线          ← 事件驱动
   [Agent] ⇄ 发布/订阅 ⇄ [中心路由] ⇄ [Agent]

5. Shared State            共享状态          ← 完全去中心
   [Agent][Agent][Agent] ⇄ 共享存储（无中心协调者）
```

---

### 1. Generator-Verifier（生成器–验证器）

**定义**：一个 Agent 产出，另一个按**明确标准**评估，反馈回去修改，直到通过或达迭代上限。

| | |
|---|---|
| **强项** | 质量关键、且评判标准可量化的工作 |
| ⚠️ **弱点** | **验证器的有效性完全取决于标准定义**——标准含糊时会制造「一切尽在掌握」的错觉，其实什么都没把住 |
| **适用** | 代码生成配测试验证、事实核查、合规检查、按评分标准打分 |
| **例子** | 客服系统生成回复，按知识库准确性与品牌语气验证 |

> 这条弱点值得单独记：**验证器最大的风险不是漏检，是给你虚假的安全感**。这跟 `21_harness-design-long-running-apps` 里「把主观判断写成带阈值的可打分标准」是同一个问题的两面——标准写不实，验证器就是摆设。

### 2. Orchestrator-Subagent（编排者–子智能体）⭐ 官方推荐起点

**定义**：主 Agent 规划工作，把**有边界的子任务**派给专精子 Agent，再汇总结果。**子 Agent 完成单个任务后即终止。**

| | |
|---|---|
| **强项** | 任务分解清晰；编排者保有对目标的连贯视角 |
| ⚠️ **弱点** | **信息瓶颈**——子 Agent 的发现必须绕道编排者才能传播；**顺序执行限制吞吐** |
| **适用** | 短、聚焦、相互依赖少、输出明确的子任务 |
| **例子** | 代码审查系统：安全检查、测试覆盖率、风格、架构评估各派一个 Agent |

**「信息瓶颈」是这个模式的命门**：子 Agent A 发现的东西，子 Agent B 看不到，除非编排者转述。任务之间一旦有隐含依赖，就该考虑换模式。

### 3. Agent Teams（智能体团队）

**定义**：协调者启动多个**常驻工人**，工人从**共享队列**认领任务。**工人跨任务保留上下文，不是做完就死。**

| | |
|---|---|
| **强项** | 持续的上下文提升表现；工人会形成领域专精 |
| ⚠️ **弱点** | 自主运行导致**信息不易共享**；**完成检测变复杂**（怎么知道全干完了）；**共享资源冲突** |
| **适用** | 独立的、多步骤的、能从积累上下文中获益的子任务 |
| **例子** | 代码库框架迁移，每个 teammate 独立迁移分配到的服务 |

**与 Orchestrator-Subagent 的关键差别就一条：工人死不死。** 子 Agent 用完即弃，工人常驻。常驻带来专精，也带来「怎么判断全部完成」的新问题。

### 4. Message Bus（消息总线）

**定义**：Agent 通过中心路由**发布/订阅**事件主题。新 Agent 接入不需要重连既有连接。

| | |
|---|---|
| **强项** | 扩展灵活；支持事件驱动工作流；容纳流程的不确定性 |
| ⚠️ **弱点** | **故障追踪困难**；**错误被静默处理**；**路由准确性是命脉** |
| **适用** | 事件驱动流水线、工作流会演化、Agent 生态在增长 |
| **例子** | 安全运营系统按告警分类路由给专精调查 Agent |

### 5. Shared State（共享状态）

**定义**：Agent 通过**持久化共享存储**（数据库/文件系统）协调，自主读写。**没有中心协调者。**

| | |
|---|---|
| **强项** | 去中心化；消除单点故障；支持实时共享发现 |
| ⚠️ **弱点** | **重复劳动**；**互相矛盾的做法**；⚠️ **反应式循环会无限烧 token——除非设了明确的终止条件** |
| **适用** | 协作式研究，Agent 需要在彼此的发现上继续构建 |
| **例子** | 研究综合系统：学术、产业、专利、新闻四个 Agent 往共享知识库贡献发现 |

> **「反应式循环无限烧 token」是这五种模式里最贵的失败模式**，也是最好的面试追问答案。去中心化的代价是没人负责喊停，**终止条件必须显式设计**。

---

### ⭐ 选型决策表

| 场景 | 推荐模式 |
|---|---|
| 输出质量关键，且有明确评判标准 | **Generator-Verifier** |
| 任务分解清晰，子任务有边界 | **Orchestrator-Subagent** |
| 并行负载，独立的长时间子任务 | **Agent Teams** |
| 事件驱动流水线，Agent 生态在增长 | **Message Bus** |
| 协作研究，Agent 之间要共享发现 | **Shared State** |
| 不能有单点故障 | **Shared State** |

### ⭐ 演进决策：什么时候从 A 换到 B

| 对比 | 判据 |
|---|---|
| **Orchestrator-Subagent vs Agent Teams** | 短而聚焦的活 → 前者；子任务需要**持续的多步工作**、工人需要上下文延续 → 后者 |
| **Orchestrator-Subagent vs Message Bus** | 顺序是**预先确定**的 → 前者；工作流**从事件中涌现**、会随发现而变 → 后者 |
| **Agent Teams vs Shared State** | 各自分区、互不交互 → 前者；需要**实时访问彼此的发现** → 后者 |
| **Message Bus vs Shared State** | 离散事件流水线 → 前者；知识随时间**累积** → 后者。另外前者保留中心路由，后者完全去中心 |

### 官方给的起手式

> **从 orchestrator-subagent 开始**——它适用面最广。等生产环境暴露出具体限制，再向其他模式演进。

这句话本身就是好答案：**不要一上来就设计五种模式的混合体**，先上最通用的，让真实瓶颈决定演进方向。

## 面试怎么用

**被问「多 Agent 系统怎么设计」**：
先给五种模式的名字和一句话定义（信息流动方式的差别），再给选型表，最后给官方起手式「从 orchestrator-subagent 开始，让生产瓶颈决定演进」。

**被追问「这些模式的坑在哪」**（这是拉开差距的地方）：
- orchestrator-subagent → **信息瓶颈**，子 Agent 发现无法横向传播
- agent teams → **完成检测**和共享资源冲突
- shared state → **反应式循环无限烧 token**，必须显式设终止条件
- generator-verifier → **标准含糊时给虚假安全感**
- message bus → 故障难追踪、错误静默

**加分点**：补一句对齐博客的发现——多 Agent 组织比单 Agent 更有效但更不对齐。能主动提代价，说明不是只读了推销材料。
