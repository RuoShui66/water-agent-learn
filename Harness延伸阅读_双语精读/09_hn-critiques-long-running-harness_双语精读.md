## 一句话摘要

长时程 harness 讨论区里最一致的批评是：**LLM 几乎零成本地拿下前 70%，剩下 30% 需要昂贵的基础设施，而这个落差会给管理层制造虚假乐观**——加上一条更根本的反驳：**理解系统这件认知劳动无法外包，只能被推迟。**

## 核心内容

### 1. 70/30 帕累托问题（最主流的一条）

讨论区的主导主题。原话大意：

> 几乎不费力就能走到 **70%**，但剩下的 **30%** 需要多智能体评判系统、外部记忆、上下文管理。

另一位参与者把它框成**帕累托原则被误用**：LLM 高效处理掉了 boilerplate，但最后那 20% 的工作往往是**「对代码的复杂返工」**（complicated reworking of the code）。

**为什么这条重要**：它解释了为什么 demo 效果和生产效果差距巨大——demo 停在 70%，生产要求 100%，而那段差距恰好是 harness 成本最陡的一段。

### 2. 理解无法外包（Understanding Cannot Be Outsourced）★

本篇最有分量的一条，因为它不是抱怨工具不成熟，而是一个**结构性论证**：

> 你仍然必须投入那份工作去深刻地理解系统。你可以在写提示词的时候提前做……但**理解系统的这份工作没法外包给 LLM**。

推论：**LLM 只是改变了理解发生的时间点，并没有消除它。** 认知劳动被推迟到 code review、测试，或者生产事故的时候偿还。

📌 **这是对「把规格写好就能全托管」叙事的直接反驳**，也是综述里那条的原始出处。面试里这条最容易加分，因为它承认了技术价值同时指出了会计错误。

### 3. 成本与可扩展性

- 有用户报告：涉及**数百个不同智能体、多个模型**的复杂智能体工作流，**单次运行数百美元**（several hundred dollars per run），且**不保证可靠输出**。
- 多周的 Claude Code 长会话会吃掉顶级订阅额度，不过**具体的单次会话成本讨论中仍然含糊**。

⚠️ 注意这条的两面性：它既是反方论据，也印证了官方自己在动态工作流博客里的提醒——**工作流明显更耗 token，只适合复杂高价值任务**。两边其实是同一个结论。

### 4. 专职 QA 智能体会失效

一位资深开发者的观察：专门的测试智能体会**系统性地失败**——智能体**「卡在两个都不是你想要的选项之间来回循环」**（get stuck in a loop between two options that are both not what you want），而不是收敛到解。

他的结论是：**开发智能体必须自己处理 QA。**

📌 **这条直接顶撞了「生成/评判分离」这条核心共识**，值得单独想清楚回应。可用的回应是区分层次：**独立上下文的一次性评审子智能体**（有内部实验支持）和**常驻的专职 QA 智能体**（收敛问题真实存在）不是同一个东西。评估器不是免费午餐，需要 rubric 校准投入。

### 5. 控制的根本局限

讨论里反复出现的张力：**agency 与确定性控制之间无法调和**。基础设施复杂度成了一种隐形税（infrastructure complexity as a hidden tax）。

### 6. 反方的反方（Counterarguments）

讨论区里为 LLM 辩护的声音也值得记，因为它们划出了「什么时候确实有效」：

- LLM 替代的是**过去需要初级开发者做的工作**。
- **「功能级的自动补全」**（autocomplete at feature level）这个框架有实用价值——即智能体去实现被精确指定的高层指令。
- 长会话确实让**多周项目**在低频人工评审下推进，尽管成本高，但节省的时间是实打实的。

### 7. 反复出现的主题（Recurring Themes）

- 关于「简单性」的**炒作与现实落差**
- **agency 与确定性控制**之间的持久张力
- **基础设施复杂度是一种隐形税**
- **项目管理结构**（thin slicing、清晰的归属）反而成了必要的脚手架 —— 即：**有些脚手架是组织层面的，不是技术层面的**

## 可直接带走的工程结论

1. **给管理层汇报时区分 70% 和 100%**——demo 到生产的成本曲线是非线性的，最后 30% 才是 harness 预算所在。
2. **理解的债务会被推迟而不是消除**，排期时要给 review 和事故留出这份成本。
3. **多智能体不是默认选项**：数百美元单次运行的报告和官方「工作流更耗 token」的提醒指向同一个结论——**并行必须挣回它的协调成本**。
4. **区分「一次性独立评审」和「常驻 QA 智能体」**：前者有实验支持，后者有真实的收敛失败报告。
5. **评估器需要 rubric 校准投入**，不校准就会陷入两个坏选项之间的循环。
6. **一部分必要脚手架是组织性的**（thin slicing、明确归属），不是写代码能解决的。
