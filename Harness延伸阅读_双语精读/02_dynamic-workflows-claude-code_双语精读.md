## 一句话摘要

与其让所有任务共用一套通用 harness，不如让 Claude **为手头这个任务现场写一套编排代码**——生成一个 JavaScript 编排文件来派生和协调子智能体，每个子智能体有独立上下文窗口、可单独选模型、可选是否隔离在独立 worktree 里。

## 核心内容

### 1. 什么是动态工作流

关键区别一句话说清：**静态工作流要你预先搭好一套通用设计；动态工作流让 Claude 按需自己写一套专用的**。

编排层能力包括：标准 JavaScript 工具（JSON / Math / Array）、**按子智能体选择智能等级**、决定是否用 worktree 隔离、以及**可恢复执行**（中断后能从中途续跑）。

触发方式：直接说「Create a workflow…」，或者用关键词 **`ultracode`** 保证 Claude 一定生成工作流。

### 2. 六种组合模式（本文最值得背的部分）

| 模式 | 做什么 | 典型场景 |
|---|---|---|
| **Classify-and-act** | 先分类，再按类别路由给专门的智能体 | 工单分诊、模型路由 |
| **Fan-out-and-synthesize** | 拆成许多小步，每步跑一个智能体，最后综合 | 大批量工作，且各步之间不该互相污染 |
| **Adversarial verification** | 每派生一个智能体，就再派生一个**专门去按评分标准反驳它的产出** | 结论正确性要求高时 |
| **Generate-and-filter** | 先产出多个候选，再按质量/去重/评分标准过滤 | 需要多样性再筛选 |
| **Tournament** | 派生 N 个智能体各用不同方法做同一件事，再**两两比对评判** | 设计、命名这类没有唯一解的任务 |
| **Loop-until-done** | 持续派生直到满足停止条件（没有新发现、零错误） | 开放式发现类工作，事先不知道有多少 |

**adversarial verification 和 tournament 是三月文章里没有的新东西**：三月的评估器是「一个评审对一个产出」，这里升级成了「多个独立视角互相攻击」和「多个方案捉对厮杀」。

### 3. 它防的三种失败模式

这三个名字值得原样记住，因为它们精确对应 2025-11 与 2026-03 两篇文章诊断出的病症：

- **Agentic laziness**（智能体偷懒）：Claude 提前停手，把做了一半说成全部完成。
- **Self-preferential bias**（自我偏袒）：Claude 倾向偏爱自己的结果，**尤其是在被要求验证或评判它们的时候**。
- **Goal drift**（目标漂移）：多轮之后对原始目标的忠实度逐渐流失——摘要步骤丢细节，约束慢慢淡掉。

三者都是**单一上下文窗口的固有病**，所以解法是换上下文窗口，而不是在同一个窗口里加更多指令。

### 4. 什么时候用

官方点名的场景：迁移与重构（Bun 的 Zig→Rust 重写用了工作流）、深度研究（扇出搜索 + 对抗式事实核查）、大规模验证（给文档里每个论断找出处）、排序与排名（1000+ 条目的两两比较锦标赛）、规则遵从性检查（每条规则配一个专职校验智能体）、根因调查（多个独立假设并行验证）、分诊流程、探索与品味类选择、轻量 eval、模型路由。

### 5. 什么时候不用（同样重要）

官方给的自检问题很实用：**「这个任务真的需要更多算力吗？」**

工作流**明显更耗 token**，官方明说它适合复杂高价值任务。常规编码任务不要用。原则一句话：**并行与专业化必须挣回它们的协调成本**（*"parallelism and specialization have to earn their coordination cost"*）。

成本可以显式控制——提示里写 "use 10k tokens" 就能设上限，让它在预算内尽量并行。

### 6. 工程细节

- **保存**：工作流菜单里按 `s` 保存，存到 `~/.claude/workflows`，或者打包进 skill 分发（把 JS 文件放进 skill 目录并在 `SKILL.md` 里引用）。
- **与其他命令组合**：配 `/loop` 做周期性任务（分诊、研究），配 `/goal` 做硬性完成要求。
- **模板 vs 脚本**：分发时可以写成模板化提示词保留灵活性，也可以写成刚性脚本保证确定性。

## 可直接带走的工程结论

1. **对抗式验证要让验证者带着「去反驳」的任务上场**，而不是问「这个对吗」。
2. 多个独立视角 > 一个评审重复跑——**视角多样性能抓到冗余抓不到的失败模式**。
3. 开放式发现用 loop-until-done（连续 K 轮无新发现才停），不要用「找 N 个就停」的计数器——**计数器会漏掉长尾**。
4. 编排要设显式 token 预算，并且**默认不用**：让并行自己证明它值得。
5. 三种失败模式是上下文窗口的属性，不是提示词能修的——**换窗口，别加指令**。
