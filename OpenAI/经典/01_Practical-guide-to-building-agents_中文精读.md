## 一句话摘要

先验证任务是否真的需要自主决策，再用“模型 + 工具 + 指令”构建一个能循环执行的单 Agent；只有当提示和工具选择复杂到明显失效时，才引入多 Agent，并始终用分层护栏与人工接管控制风险。

## 什么才算 Agent

指南把 Agent 定义为能够代表用户独立完成任务的系统。一个普通 LLM 应用如果只是回答问题、分类或生成文本，但不负责控制工作流，就不属于这里讨论的 Agent。

Agent 有两个关键特征：

1. LLM 管理工作流执行和决策，能够判断何时完成、何时修正、何时停止并交还控制；
2. 它能根据当前状态动态选择工具读取信息或执行动作，并受明确护栏约束。

## 什么时候值得构建 Agent

指南建议优先寻找传统自动化很难处理的流程：

- 需要细致判断、例外处理或上下文敏感决策；
- 规则系统已经庞杂、昂贵且容易出错；
- 大量依赖自然语言、文档等非结构化数据。

如果流程稳定、规则清楚、结果容易通过确定性代码得到，就不应为了“Agent 化”而增加不确定性。

## 三个设计基础

### Model

先用最强模型建立质量基线，再在有 eval 的前提下尝试用更小模型替代部分步骤。优化顺序应是先满足准确率，再优化成本与延迟。

### Tools

工具大体包括读取上下文的数据工具和改变外部系统的动作工具。工具定义要标准化、文档清楚、可复用，并对高风险写操作设置额外检查。

### Instructions

把现有 SOP、政策和支持脚本转成清晰步骤；每一步对应具体动作；提前写出信息缺失和边界情况的处理方法。指令应减少歧义，但不要把模型变成难以维护的伪规则引擎。

## 单 Agent 与多 Agent

默认先扩展一个 Agent 的工具和提示，因为单 Agent 更容易评测、维护和理解。只有当它持续无法遵守复杂指令、经常选错工具，或不同职责需要明显隔离时再拆分。

指南给出两类多 Agent 模式：

- **Manager pattern**：中心 Agent 保持与用户交互，把专家 Agent 当作工具调用并汇总结果；
- **Decentralized / handoff pattern**：当前 Agent 把会话控制权交给另一个 Agent。

## 护栏

护栏是多层防御，而不是一个“安全提示词”。可组合相关性检查、安全分类、PII 过滤、内容审核、工具风险分级、规则检查和输出校验。对于失败次数过多、不可逆或高影响动作，应触发人工介入。

## 可直接带走的工程原则

- 先写出不用 Agent 的确定性方案，再说明它为什么不够。
- 每个 Agent 都应有清楚的退出条件、最大轮数和人工接管路径。
- 对读取、可逆写入、不可逆写入分别设定权限和审批策略。
- 先单 Agent，再基于可测量失败拆分职责。
- 模型降级或路由必须基于 eval，而不是只看单次演示。

## 为什么是经典

它把早期 Agent 讨论中容易混乱的概念收束成一个简单框架，适合作为整个阅读包的 OpenAI 侧入口。
