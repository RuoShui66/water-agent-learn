# 07_编排智能体：例程与交接_面试速记

> OpenAI Cookbook · [官方原文](https://cookbook.openai.com/examples/Orchestrating_agents) · [本地逐句对照](07_Orchestrating%20Agents%20Routines%20and%20Handoffs_编排智能体：例程与交接_逐句对照.md)

## 一句话讲明白

**当一个提示词要塞进太多互不相干的流程时，别再往里堆——把它拆成多段「例程」（一份自然语言步骤清单 + 完成这些步骤所需的工具），每段例程就是一个智能体；再让智能体之间用「交接」互相转手对话。交接的实现巧到只有一行判断：工具函数不返回字符串，而是返回一个 `Agent` 对象，主循环发现返回值类型是 `Agent` 就把当前智能体换掉。**

## 为什么值得读 / 能用在哪

- 这是 **OpenAI 多智能体思路的原点文档**。文末给出的示例库 Swarm 就是这套代码的打包版（原文明说：仅作示例，不应直接用于生产环境），而 Swarm 的核心抽象——智能体 = 指令 + 工具、交接 = 一个能返回智能体的工具——后来被沿用进 OpenAI 的正式智能体框架里。面试聊「多智能体怎么落地」，这篇是最短的一条路径。
- 它没有任何框架依赖：全篇就是 `client.chat.completions.create` + 一个 `while` 循环 + 几十行反射代码。**你能在白板上把整套机制画完**，这在面试里非常吃香。
- 落到自己项目：任何「客服分流 / 工单分类 / 多部门业务」的场景都可以直接照抄这个拓扑——一个分诊智能体在前，若干专职智能体在后，外加一个升级到人工的出口。

## 核心要点

### 1. 例程（routine）：把提示词当状态机写

原文对例程的定义刻意保持朴素：**一份用自然语言写的指令清单（用系统提示词承载），外加完成这些指令所需要的工具**。你叫它例程、智能体、助手都行，概念是同一个。

原文的客服例程长这样（四步，带条件分支）：

```python
system_message = (
    "You are a customer support agent for ACME Inc."
    "Always answer in a sentence or less."
    "Follow the following routine with the user:"
    "1. First, ask probing questions and understand the user's problem deeper.\n"
    " - unless the user has already provided a reason.\n"
    "2. Propose a fix (make one up).\n"
    "3. ONLY if not satisfied, offer a refund.\n"
    "4. If accepted, search for the ID and then execute refund."
)
```

**这一节要记住的判断**：

- 这些指令里的条件判断「很像状态机或者代码中的分支」——但它跑在大语言模型上。
- 对**中小规模**的例程，模型能相当稳健地处理这类分支，而且额外带来一个真状态机没有的好处：**「柔性」遵循**——模型可以自然地引导对话走向，不会卡进死胡同。
- 反过来，这也是全文的痛点起点：**例程一旦塞进太多不同任务，就会开始力不从心**。

### 2. 执行循环：一轮 = 「调模型 → 有工具调用就执行并回填 → 直到没有工具调用」

工具是普通 Python 函数，用 `inspect.signature` 反射出签名自动转成模型要的函数描述格式（function schema）：**函数名当工具名，docstring 当工具描述，没有默认值的参数进 `required`**。这个细节后面很关键。

一整轮的骨架（原文 `run_full_turn` 的核心，去掉重复部分）：

```python
while True:
    response = client.chat.completions.create(
        model=agent.model,
        messages=[{"role": "system", "content": agent.instructions}] + messages,
        tools=tool_schemas or None,
    )
    message = response.choices[0].message
    messages.append(message)

    if not message.tool_calls:   # 没有工具调用了，本轮结束
        break

    for tool_call in message.tool_calls:
        result = execute_tool_call(tool_call, tools_map)
        messages.append({"role": "tool",
                         "tool_call_id": tool_call.id,
                         "content": result})
```

注意两个工程细节：函数只返回**本轮新增的消息**（`messages[num_init_messages:]`），由外层对话循环负责合并；`tools_map` 是「工具名 → Python 函数对象」的反查表，工具调用就是查表 + `**args` 解包。

### 3. 例程 = 智能体：一个四字段的数据类

把系统提示词和工具收进一个对象，「例程」就变成了「智能体」：

```python
class Agent(BaseModel):
    name: str = "Agent"
    model: str = "gpt-4o-mini"
    instructions: str = "You are a helpful Agent"
    tools: list = []
```

**四个字段——名字、模型、指令、工具**。这就是这篇文章对「智能体」给出的全部定义，没有第五个概念。`run_full_turn` 相应地从收三个参数改成收一个 `agent`，循环逻辑一行没改，只是配置来源换成了智能体自身。

一个直接的收益马上就出现了：**消息历史是共享的，智能体是可换的**。原文的演示是先用销售智能体处理「下单买黑靴子」，再把**同一份 `messages`** 交给退款智能体处理「我要退款」——退款智能体能隐式理解「那件商品」指的是刚才那双靴子。用原文的比喻：交接就像打电话被转接给另一个人，**只不过接手的智能体对你之前的对话了如指掌**。

### 4. 交接（handoff）的巧妙设计：让工具返回一个 `Agent` 对象

上面那次切换是**手动**的，我们要的是智能体自己决定何时交接。原文给的做法分两步。

**第一步——让模型能表达交接的意图**：给它一个 `transfer_to_XXX` 函数。原文的评价是「简单却出奇有效」，理由很实在：**模型足够聪明，知道在该做交接的时候去调用这个函数**。

**第二步（全文最关键的一步）——让交接真的发生**。已有的工具（`execute_refund`、`place_order`）返回的都是字符串，字符串会被喂回给模型。那如果**改成返回一个 `Agent` 对象**呢？

```python
def transfer_to_refunds():
    return refund_agent      # 不返回字符串，直接返回 Agent 对象

# 主循环里只需要加一个类型判断：
for tool_call in message.tool_calls:
    result = execute_tool_call(tool_call, tools, current_agent.name)

    if type(result) is Agent:            # 返回值是 Agent，就换人
        current_agent = result
        result = f"Transfered to {current_agent.name}. Adopt persona immediately."

    messages.append({"role": "tool",
                     "tool_call_id": tool_call.id,
                     "content": result})
```

**这个设计为什么漂亮，面试时按四点讲：**

1. **用返回值的类型承载控制流**。工具的返回值本来只是数据（喂回模型的字符串），这里让它多态成一条控制指令。整个交接机制的增量就是 `if type(result) is Agent` 这一行。
2. **零新概念**。不需要给模型引入「交接」这种新原语——在模型眼里它调的还是一个普通函数。交接完全发生在调用方的代码里，模型侧无感。
3. **切换的是配置，不是会话**。切换后下一次循环用的是 `current_agent.instructions` 和 `current_agent.tools`，而 `messages` 原封不动继续往下走。所以说**系统提示词和工具集被换掉了，对话没断**。
4. **交接后立刻给模型一句话定身份**：工具结果被替换成 `Transfered to X. Adopt persona immediately.`（「已转交给某某，立即代入该角色」），确保新智能体不会用旧口吻继续说话。

配套还需要一个小容器 `Response`（两个字段：`agent` 和 `messages`），把「本轮结束时是谁在当值」和「本轮新增的消息」一起带回给外层。外层主循环因此变成三行：`response = run_full_turn(agent, messages)` → `agent = response.agent` → `messages.extend(response.messages)`。**交接结果靠 `response.agent` 跨轮次保持下来**，这是整个系统能持续运行的闭环。另外注意：类型判断在**内层**循环里，所以同一轮之内可以连续交接多次。

### 5. 分诊智能体（triage agent）模式：一个入口、若干专职、两个出口

原文最后给的完整拓扑，是这套设计最直接的产品形态：

```python
def transfer_to_sales_agent():
    """User for anything sales or buying related."""
    return sales_agent

def transfer_back_to_triage():
    """Call this if the user brings up a topic outside of your purview,
    including escalating to human."""
    return triage_agent

triage_agent = Agent(
    name="Triage Agent",
    instructions=("You are a customer service bot for ACME Inc. "
                  "Introduce yourself. Always be very brief. "
                  "Gather information to direct the customer to the right department. "
                  "But make your questions subtle and natural."),
    tools=[transfer_to_sales_agent, transfer_to_issues_and_repairs, escalate_to_human],
)
```

结构拆开看：

- **分诊智能体**：自己不办业务，只有三个工具，全是转接。它的指令核心是「收集信息把客户导向正确的部门，但问题要问得含蓄自然」。
- **两个专职智能体**：销售智能体（工具 `execute_order`）和问题维修智能体（工具 `execute_refund`、`look_up_item`），各自带自己那段四步例程。
- **两个出口**：每个专职智能体都带 `transfer_back_to_triage`，用来把超出职责范围的话题退回分诊；`escalate_to_human` 打印一份升级报告后终止流程，是升级人工的出口。
- **模型凭什么知道该转给谁**：靠 `transfer_to_XXX` 函数的 **docstring**——因为 docstring 就是工具描述。所以「什么时候交接」这条业务规则，实际写在注释里。这也是这套设计里最容易被忽略、但面试可以点出来的一处：**路由逻辑的载体是工具描述，不是提示词**。

### 6. 为什么这套设计比一个大提示词更可控

原文的动机只有一句「例程塞太多任务会力不从心」，但把机制想透之后，可控性的来源可以拆成四条，面试时这段最能体现判断力：

- **指令短，分支少**。每个智能体只面对自己那 4 步流程，不用在一个提示词里维护「如果是销售就……如果是退款就……」的巨型分支树。
- **工具集是硬隔离**。销售智能体的请求里**根本不包含** `execute_refund` 的 schema——它不是「被要求别调」，而是**压根看不见**。用一个大提示词做不到这一点：所有工具都在 schema 里，你只能靠自然语言约束模型别乱调。这是权限收窄，不是行为劝导。
- **改动是局部的**。改销售话术不会影响退款流程；加一个新部门就是加一个 `Agent` 和一个 `transfer_to_XXX`，别的智能体一个字不用动。
- **日志天然带身份**。原文打印用的是 `print(f"{current_agent.name}:", ...)`——每一句输出、每一次工具调用都带着当值智能体的名字，出问题时能立刻定位是哪一段例程的锅。

## 横向对照：OpenAI 的交接 vs Anthropic 的编排者-工作者

**这是本批最值得单独准备的一个对照点**，面试被问「多智能体你会怎么设计」时，先把这两条路线摆出来，再说选哪条、为什么。

| 维度 | OpenAI：交接（handoff） | Anthropic：编排者-工作者（orchestrator-workers） |
|---|---|---|
| 控制权 | **转移**。交接后原智能体退场，`current_agent` 换人 | **保留**。编排者始终持有控制权，子智能体只是被派活的工作者 |
| 拓扑 | 去中心化的**链**：任意时刻只有一个智能体在跑 | 中心化的**树**：一主多子，子智能体并行 |
| 上下文 | **共享同一份 `messages`**，接手方全知道之前说了什么 | 子智能体**各自独立的上下文窗口**，只把压缩后的结论回传 |
| 收敛方式 | 谁接手谁负责回答，**没有汇总环节** | 编排者综合所有子智能体结果，不够就再开一轮 |
| 适用场景 | **职责边界清晰的分流**：客服分部门、工单分类、按意图路由 | **需要汇总的并行任务**：多来源调研、批量核对、全库扫描 |
| 成本 | 与单智能体基本同量级（同一份历史，串行推进） | Anthropic 给的数字是 token 用量约为普通聊天的 **15 倍**，换来内部研究评估 **+90.2%** |

**失败模式完全不同**（这一段比表格更能加分）：

- 交接的典型故障是**转错部门**和**乒乓来回**——因为每个专职智能体都带 `transfer_back_to_triage`，一旦分诊判断反复摇摆，对话就会在两个智能体之间弹来弹去，用户什么也没得到。另一类是**交接后不认账**：新智能体拿到全部历史，却用自己的口径重新理解了一遍（原文正是靠那句「立即代入该角色」来压这个问题）。
- 编排者-工作者的典型故障是**委派写不清导致重复劳动**——Anthropic 的原文案例是主智能体只说「研究一下半导体短缺」，结果一个子智能体去查 2021 年汽车芯片危机、另外两个在重复查 2025 年供应链；以及**简单查询过度投入**（早期为一个简单问题派生 50 个子智能体）。

**可观测性也不同**：

- 交接系统的链路是**单线程的一条链**，任意时刻只有一个当值智能体，日志读起来就是一条时间线，问题容易复现——代价是你看不到「别的方案会怎样」，因为根本没有并行分支。
- 编排者-工作者是**并行的树**，同一个起点可能走出完全不同但同样有效的路径，所以不能拿「有没有按预设步骤执行」来判分；Anthropic 明确说要监控**智能体的决策模式和交互结构**，并且系统存在**涌现行为**——动一下主智能体，子智能体的行为会以难以预测的方式变化。

**面试可以直接抛的结论**：这两者不是二选一，而是**分层**——外层用交接做意图路由（便宜、可控、边界清晰），某个专职智能体内部要做广度调研时再局部起一个编排者-工作者（贵，但换并行覆盖）。判断依据只有一条：**这一步需要的是「换个人来办」还是「找一群人一起查再汇总」**。

## 面试高频问答

**Q：交接具体是怎么实现的？讲讲机制。**
A：给智能体一个 `transfer_to_XXX` 工具，但这个工具不返回字符串，而是返回目标 `Agent` 对象。主循环执行完工具后加一句 `if type(result) is Agent` 判断，命中就把 `current_agent` 换成返回的那个，并把工具结果替换成「已转交给某某，立即代入该角色」。下一次循环就改用新智能体的指令和工具，而 `messages` 一直共享不断。整个增量就是一行类型判断——模型侧完全无感，它以为自己只是调了个普通函数。

**Q：为什么不干脆写一个大提示词，把所有分支都写进去？**
A：三点。第一，中小规模的例程模型能稳健处理，但任务一多就会力不从心，这是原文的直接结论。第二也是最硬的一点：**工具集是硬隔离**——销售智能体的请求里压根不包含退款工具的 schema，这是权限收窄，而大提示词只能靠自然语言劝模型别乱调。第三，改动局部化，加一个部门只是加一个 `Agent` 加一个转接函数，其他智能体一个字不用动。

**Q：模型凭什么知道该交接给谁？**
A：靠 `transfer_to_XXX` 函数的 docstring。这套代码用反射把 Python 函数转成函数描述格式，函数名当工具名、**docstring 当工具描述**。所以路由规则实际是写在注释里的，比如「User for issues, repairs, or refunds」。这也意味着调路由效果的抓手是改 docstring，而不是改系统提示词。

**Q：分诊智能体模式怎么搭？**
A：一个分诊智能体在前，自己不办任何业务，只持有转接工具，指令是「收集信息把客户导向正确部门，但问题问得含蓄自然」；后面挂若干专职智能体，各带自己的业务工具和四步例程。再留两个出口：每个专职智能体都带 `transfer_back_to_triage`，用于把超出职责的话题退回；另有 `escalate_to_human` 升级人工。

**Q：OpenAI 的交接和 Anthropic 的编排者-工作者怎么选？**
A：看控制权要不要转移。交接是去中心化的，控制权转手、只有一个智能体在跑、共享同一份历史，适合职责边界清晰的分流；编排者-工作者是中心化的，编排者始终握着控制权，子智能体带独立上下文并行干活再汇总，适合需要广度覆盖和汇总的任务，代价是 token 约 15 倍。失败模式也不一样：前者容易转错部门和来回踢皮球，后者容易委派不清导致重复劳动。实际做法通常是分层——外层交接做路由，内层需要广度时再局部起编排者-工作者。

## 必须记住的 8 句话

1. **例程 = 一份自然语言的步骤清单（系统提示词）+ 完成它所需的工具**，没有更玄的定义。
2. 例程里的条件分支「很像状态机」，但比状态机多了**柔性遵循**——模型不会卡进死胡同。
3. 智能体在这篇文章里只有**四个字段**：名字、模型、指令、工具。
4. **交接的全部实现就是：工具返回 `Agent` 对象，主循环判断 `type(result) is Agent` 就换 `current_agent`。**
5. 交接换的是**系统提示词和工具集**，`messages` 共享不断——所以接手方对之前的对话了如指掌。
6. 交接后要立刻塞一句「已转交给某某，**立即代入该角色**」，否则新智能体会用旧口吻说话。
7. 分诊模式 = 一个只会转接的分诊智能体 + 若干专职智能体 + `transfer_back_to_triage` 和 `escalate_to_human` 两个出口；**路由规则写在 docstring 里**。
8. 交接是**控制权转移**（去中心化、链状、共享上下文），编排者-工作者是**控制权保留**（中心化、树状、独立上下文再汇总）——前者适合分流，后者适合汇总。

## 30 秒口述版

> 这篇 Cookbook 讲的是：当一个提示词要装下太多互不相干的流程时，别再往里堆，而是拆成多段「例程」——每段例程就是一份自然语言步骤清单加上完成它需要的工具，把它们收进一个只有名字、模型、指令、工具四个字段的 `Agent` 类，例程就变成了智能体。然后用「交接」让智能体之间自己转手对话：给每个智能体一个 `transfer_to_XXX` 工具，这个工具不返回字符串而是返回目标 `Agent` 对象，主循环里加一行 `if type(result) is Agent` 就把当前智能体换掉，同时把工具结果替换成「立即代入该角色」。妙在模型侧完全无感——它以为只是调了个普通函数，控制流却已经转手了；而且换的只是系统提示词和工具集，消息历史一直共享，接手方对之前说过什么了如指掌。最终形态是分诊智能体模式：一个只会转接的分诊智能体在前，若干专职智能体在后，加上退回分诊和升级人工两个出口，路由规则就写在转接函数的 docstring 里。它比一个大提示词可控，关键在于工具集是硬隔离——不该被调的工具压根不在请求的 schema 里。这套代码被打包成了示例库 Swarm，也是后来 OpenAI 智能体框架的思想源头。
