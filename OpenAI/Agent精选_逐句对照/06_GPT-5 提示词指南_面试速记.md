# 06_GPT-5 提示词指南_面试速记

> OpenAI Cookbook · [官方原文](https://cookbook.openai.com/examples/gpt-5/gpt-5_prompting_guide) · [本地逐句对照](06_GPT-5%20prompting%20guide_GPT-5%20提示词指南_逐句对照.md)

## 一句话讲明白

**GPT-5 能在「全权放手」到「管得死死的」这条光谱上的任意位置工作，所以提示词工程的核心动作不再是「把话说满」，而是给智能体（agent）设一个明确的档位——用 `reasoning_effort`（推理力度）和 `verbosity`（详略度）两个 API 参数定粗调，用 `<context_gathering>`、`<persistence>`、`<tool_preambles>` 这类结构化提示词块定细调，再用自我反思（self-reflection）提质量、用元提示（metaprompting）让模型自己改提示词。**

## 为什么值得读 / 能用在哪

- 这是本批文章里**对日常工作最能直接抄的一篇**：它给的不是理念，是可以复制粘贴的提示词块和参数档位。
- 你现在做的智能体，八成正卡在两个极端之一——要么疯狂搜索半天不出活（探索过度），要么动不动回头问你「要不要继续」（自主性不足）。这篇把两个方向的调法都写死了。
- 面试里最容易加分的点：**能说出「调参数」和「写提示词」分别负责什么，以及两者怎么配合**（Cursor 的全局低详略度 + 编程工具高详略度就是标准答案）。
- 还有一条反直觉结论特别好用：**对 GPT-5 来说，写得糟糕的提示词比对旧模型伤害更大**——因为它会认真去调和矛盾，而不是随便挑一条执行。

## 核心要点

### 1. 智能体的「放手程度」（agentic eagerness）：一条光谱，两个方向调

智能体脚手架（agentic scaffold）在控制力度上横跨一条很宽的光谱：一端把决策权几乎全交给模型，另一端用大量程序化逻辑分支把模型管死。GPT-5 训练时就是奔着「光谱上任意位置都能跑」去的。

所谓「放手程度」，说白了就是**模型在「主动出击」和「等待明确指示」之间的平衡点**。默认状态是：为了保证答案正确，它收集上下文时会做得非常彻底、非常全面——这在小任务上就是浪费。

**要它少主动（降低延迟、减少跑偏的工具调用）**：

- 调低 `reasoning_effort`。探索深度降下来，效率和延迟上去。**很多工作流在 medium 甚至 low 档位就能稳定跑出好结果。**
- 在提示词里明确写清楚「你希望它怎么探索问题空间」，减少它发散权衡的必要。

**要它多主动（长周期任务、减少反问）**：调高 `reasoning_effort`，再加一段坚持度（persistence）提示词。

### 2. 上下文收集的深浅权衡：给判据，给预算，给逃生舱口

原文的长版 `<context_gathering>`（上下文收集）提示词干了这么几件事：先粗后细、并行发多路查询、去重缓存路径；给**提前停止的判据**（能点名要改的具体内容，或搜索结果约 **70%** 收敛到同一区域）；只允许在信号冲突时**额外升级一轮**；追踪深度只到你要改的符号；最后规定「批量搜索 → 最小计划 → 完成任务」的循环，并强调**行动优先于继续搜索**。

如果愿意把规则定得再死一点，就直接卡预算——**这个短版最值得背下来**：

```
<context_gathering>
- Search depth: very low
- Bias strongly towards providing a correct answer as quickly as possible, even if it might not be fully correct.
- Usually, this means an absolute maximum of 2 tool calls.
- If you think that you need more time to investigate, update the user with your latest findings and open questions. You can proceed if the user confirms.
</context_gathering>
```

**什么场景用**：延迟敏感的问答型智能体、客服、代码搜索这类「答得快比答得全更重要」的场合。
**为什么这么写**：四行分别对应四件事——**定档位**（搜索深度极低）、**定倾向**（宁快勿全）、**定硬上限**（最多 2 次工具调用）、**定溢出出口**（超预算就把当前发现同步给用户等确认，而不是偷偷继续搜）。
**最关键的一句是 `even if it might not be fully correct`**——这就是原文说的**逃生舱口（escape hatch）**：限制上下文收集时，必须明确允许模型「在不确定的情况下继续推进」，否则它会为了满足「必须正确」而突破你给的预算。这是这篇文章里最容易被面试官追问的细节。

### 3. 反方向：坚持度提示词，把活儿钉在模型手上

```
<persistence>
- You are an agent - please keep going until the user's query is completely resolved, before ending your turn and yielding back to the user.
- Only terminate your turn when you are sure that the problem is solved.
- Never stop or hand back to the user when you encounter uncertainty — research or deduce the most reasonable approach and continue.
- Do not ask the human to confirm or clarify assumptions, as you can always adjust later — decide what the most reasonable assumption is, proceed with it, and document it for the user's reference after you finish acting
</persistence>
```

**什么场景用**：长周期（long horizon）编程任务、批量处理、无人值守的执行链路（rollout）。
**为什么这么写**：四条是层层递进的堵漏——先定义身份（你是智能体，不是问答机器人），再定终止条件（确信解决才收工），再堵「遇到不确定就停」，最后堵「反问用户确认假设」。注意最后一条给了模型一个心理台阶：**「你随时可以后面再调整」+「做完把假设记录下来」**——不是禁止它有疑问，而是把疑问从「打断流程」改成「事后备案」。

配套要写清三件事：**停止条件、哪些动作安全哪些不安全、什么情况下允许交还控制权**。原文的例子非常好用——购物工具里，**结账和支付**触发「找用户确认」的不确定性阈值要显式设低，**搜索**的阈值要设得极高；编程场景里，**删除文件**的阈值就该比 `grep` 搜索低得多。**同一个智能体内部，不同工具的自主性阈值应该是不同的。**

### 4. 工具前导语（tool preamble）：让用户跟得上

在用户会盯着看的执行轨迹（trajectory）里，模型时不时汇报「我正用工具做什么、为什么」，能大幅改善体验——**执行链路越长，这些汇报的价值越大**。GPT-5 是专门训练过输出这类「工具前导语」的。

```
<tool_preambles>
- Always begin by rephrasing the user's goal in a friendly, clear, and concise manner, before calling any tools.
- Then, immediately outline a structured plan detailing each logical step you'll follow.
- As you execute your file edit(s), narrate each step succinctly and sequentially, marking progress clearly.
- Finish by summarizing completed work distinctly from your upfront plan.
</tool_preambles>
```

**什么场景用**：任何有人在旁边看进度的智能体产品（编程助手、研究助手、自动化流程面板）。
**为什么这么写**：四句话对应交互体验的四个时间点——**开工前复述目标**（让用户确认没理解偏）、**开工前给结构化计划**（建立预期）、**过程中按序叙述**（可跟随）、**结尾总结且与开头计划明确区分**（让用户能对照「计划 vs 实际」）。最后那个「distinctly」是点睛之笔：如果总结跟计划长得一样，用户就无法判断到底做没做。

频率、风格、内容都可以在提示词里调——从「每一次工具调用都详细解释」到「只在开头给一份简短计划」。

### 5. 推理力度与详略度：两个正交的旋钮

这是全文最该记住的一组区分：

| 参数 | 控制什么 | 默认值 | 怎么调 |
|---|---|---|---|
| `reasoning_effort` | 模型**思考**的深度，以及它调用工具的积极性 | `medium` | 复杂多步任务往上调；延迟敏感往下调 |
| `verbosity` | 模型**最终答案**的长度（不是思考的长度） | —— | 全局设低，再用自然语言在特定场景覆盖 |

两条补充结论：

- **把彼此独立、可拆分的任务分散到多个智能体轮次（agent turn）里、一个轮次做一件任务时，性能达到峰值。** 别把五件事塞进一轮。
- GPT-5 首次引入 **`minimal`（最小）推理力度**——最快的档位，同时仍保有推理模型范式的好处。它是**延迟敏感用户和现有 GPT-4.1 用户的最佳升级选择**。但注意：**minimal 档下表现随提示词变化的幅度，比高档位剧烈得多**，所以要额外补四件事：① 让它在最终答案开头用项目符号列表简述思路；② 要求详尽的工具前导语；③ 最大限度消除工具指令歧义 + 插入坚持度提醒（防止提前收工）；④ 由提示词驱动的规划（因为它可用于内部规划的推理 token 变少了）。

**Cursor 的做法是「参数 + 提示词」双管齐下的教科书案例**：他们发现模型文本输出偏啰嗦（状态更新和任务后总结打断用户节奏），但工具里产出的代码又因为太精简而难读（满屏单字母变量名）。解法是——**把 `verbosity` 全局设为 low，再用提示词只在编程工具里要求高详略度**：

```
Write code for clarity first. Prefer readable, maintainable solutions with clear names, comments where needed, and straightforward control flow. Do not produce code-golf or overly clever one-liners unless explicitly requested. Use high verbosity for writing code and code tools.
```

**为什么这么写**：`verbosity` 参数只是整次执行的**默认值**，GPT-5 经过训练能响应提示词里用自然语言写的**局部覆盖指令**。所以正确姿势是「参数管全局基线，提示词管场景例外」，而不是二选一。

### 6. 自我反思（self-reflection）：让模型先造一把尺子再量自己

```
<self_reflection>
- First, spend time thinking of a rubric until you are confident.
- Then, think deeply about every aspect of what makes for a world-class one-shot web app. Use that knowledge to create a rubric that has 5-7 categories. This rubric is critical to get right, but do not show this to the user. This is for your purposes only.
- Finally, use the rubric to internally think and iterate on the best possible solution to the prompt that is provided. Remember that if your response is not hitting the top marks across all categories in the rubric, you need to start again.
</self_reflection>
```

**什么场景用**：从 0 到 1 一次成型（one shot）生成应用、生成长文档、任何「没有现成测试可跑但质量差异很大」的开放式产出。
**为什么这么写**：三步是有顺序依赖的——**先造评分表（rubric）再动手**，而不是做完再自评；评分表要 **5–7 个类别**（太少覆盖不住，太多注意力被稀释）；**明确说明不展示给用户**，避免模型把内部质量标准当成交付物输出；最后设一条硬线——**任何一个类别没拿满分就推倒重来**。本质是在没有外部验证信号的场景里，让模型**自己造一个可迭代的验证信号**。

### 7. 指令遵循：矛盾的提示词对 GPT-5 伤害更大

GPT-5 遵循指令的精度「堪比外科手术」，但这把双刃剑的另一面是——**写得糟糕、包含自相矛盾或含糊指令的提示词，对 GPT-5 的伤害比对其他模型更大**：它会耗费推理 token 去寻找调和矛盾的办法，而不是随便挑一条执行。

原文的医疗排期助手（CareFlow Assistant）例子，两处冲突要能复述：

1. 「未在病历中记录患者明确同意，绝不安排预约」 vs 「作为降低风险的第一步，不联系患者就自动分配当天最早的时段」。**修法**：把自动分配改到「告知患者之后」再做。
2. 「做任何动作之前必须先查患者档案」 vs 「高度紧急时立即引导拨打 911，先于任何排期步骤」。**修法**：加一条豁免——「紧急情况下不做档案查询，直接给出 911 指引」。

**这里的通用方法论叫解决指令层级（instruction hierarchy）冲突**：提示词是被不同干系人不断更新的「活文档」，所以必须定期审查。原文说已经有多位早期用户在做完这种审查后，在自己的核心提示词库里揪出歧义和矛盾，清理后 GPT-5 表现大幅提升。官方还提供了[提示词优化工具](https://platform.openai.com/chat/edit?optimize=true)专门帮你找这类问题。

### 8. 元提示（metaprompting）：让 GPT-5 改自己的提示词

```
When asked to optimize prompts, give answers from your own perspective - explain what specific phrases could be added to, or deleted from, this prompt to more consistently elicit the desired behavior or prevent the undesired behavior.

Here's a prompt: [PROMPT]

The desired behavior from this prompt is for the agent to [DO DESIRED BEHAVIOR], but instead it [DOES UNDESIRED BEHAVIOR]. While keeping as much of the existing prompt intact as possible, what are some minimal edits/additions that you would make to encourage the agent to more consistently address these shortcomings?
```

**什么场景用**：提示词已经能跑但效果不稳，你又说不清该改哪一句的时候。
**为什么这么写**：三个设计点——**① 要求模型「从自己的视角」回答**（它比你更知道哪些措辞会触发自己的哪些行为）；**② 强制它落到「具体措辞的增/删」**，而不是给一堆抽象建议；**③ 「尽量保留原提示词」+「最小化修改」**，避免它推倒重写导致你无法归因是哪一处改动生效。原文说已经有好几位用户把这样生成的修订版**直接部署到生产环境**。

### 9. 其他值得记的实操点

- **Responses API 是硬收益**：它在多次工具调用之间**保留推理过程**。仅仅是从 Chat Completions 换到 Responses API 并加上 `previous_response_id` 把之前的推理条目回传，**Tau-Bench Retail 分数就从 73.9% 提升到 78.2%**。原理是模型能回看自己的推理轨迹，节省思维链（chain-of-thought, CoT）token，不必每次工具调用后从头重建计划。该特性对所有用户开放，**包括 ZDR（零数据保留）组织**。
- **Markdown 默认不开**：API 里的 GPT-5 默认不把最终答案排版成 Markdown（为了兼容不支持渲染的应用）。要开就在提示词里明确要求，且**长对话中遵循度会衰减——每隔 3–5 条用户消息追加一次 Markdown 指令**可以保持稳定。
- **旧模型的提示词要重写**：Cursor 原来那段 `<maximize_context_understanding>`（「收集信息要彻底，回复前务必掌握全貌，必要时多问澄清问题」）在旧模型上很好用，**在 GPT-5 上却适得其反**——它本身就已经很主动，这段话导致它在小任务上反复调搜索，其实靠内部知识就够了。修法是**去掉 `maximize_` 前缀、把「彻底性」的措辞放软**。
- **结构化 XML 标签有效**：Cursor 测试中，用 `<[instruction]_spec>` 这类标签提升了指令遵循度，也方便在提示词别处引用前面定义过的章节。
- **文件编辑用 `apply_patch`**：官方强烈建议用它做文件编辑，以便**与训练分布保持一致**。

## 和 Anthropic 的对照：同一个问题，两种下手方式

两家都在解同一个痛点——**怎么让模型少做无用探索**。但抓手完全不同：

| 维度 | OpenAI（本篇） | Anthropic（《Effective context engineering》/《Claude Code 最佳实践》） |
|---|---|---|
| 核心抓手 | **给可调参数**：`reasoning_effort`、`verbosity`，加上可复制的提示词块 | **做上下文工程**：每一步甄选「尽可能小的一组高信号 token」 |
| 底层理由 | 任务难度不同，探索深度就该不同，交给开发者拧旋钮 | 模型有**注意力预算**，存在**上下文衰减（context rot）**，多一个 token 就多消耗一点 |
| 控制探索的手法 | 提示词里写死**判据 + 预算 + 逃生舱口**（约 70% 收敛就停、最多 2 次工具调用） | **即时检索（just-in-time）**：只带轻量标识符（路径、查询、链接），用到才加载 |
| 长任务怎么办 | 拆成多个智能体轮次，一轮一件事；`<persistence>` 防止提前收工 | 压缩（compaction）、结构化笔记、子智能体三件套 |
| 质量保证 | **自我反思**：模型自造评分表，不达满分推倒重来 | **可执行的验证闭环**：给一个模型自己能跑的检查（测试、退出码、截图比对） |
| 提示词写法 | 结构化 XML 块，直接、明确、有作用域 | 系统提示词写在**「恰当高度」（right altitude）**：够具体能引导，够灵活留启发式 |

**三条差异，面试时可以直接讲**：

1. **OpenAI 把控制权做成 API 参数，Anthropic 把控制权做成架构决策。** 前者是「我调档位」，后者是「我重新设计什么进上下文」。前者见效快、可 A/B；后者上限高、但要动系统设计。
2. **对「探索」的定性不同。** OpenAI 认为探索深度是个**可配置的量**，默认偏彻底，需要时收窄；Anthropic 认为探索本身在**消耗有限的注意力预算**，默认就该只保留最小高信号集合。所以 OpenAI 给的是「最多 2 次工具调用」这种硬预算，Anthropic 给的是「只维护文件路径，用到再 `grep`」这种结构性节流。
3. **但两家在「验证信号」上惊人地一致。** OpenAI 的自我反思评分表和 Anthropic 的「给它一个自己能跑的检查」，本质是同一件事——**智能体必须有一个能自我判定「做完没做好」的闭环，否则那个验证环节就变成你本人**。区别只是：有客观检查（测试、构建）就用 Anthropic 那套；没有客观检查的开放式产出（生成一个 Web 应用），就用 OpenAI 这套让模型自造尺子。

**还有一条有意思的呼应**：Cursor 把 `<maximize_context_understanding>` 措辞放软才让 GPT-5 表现变好——这和 Anthropic 说的「模型越强，人工甄选越应该越少，让聪明的模型聪明地行事」是同一个判断。**给强模型写提示词，减法往往比加法有效。**

## 面试高频问答

**Q：怎么控制一个智能体「探索过度」？**
A：三层手法。第一层调 `reasoning_effort` 到 medium 或 low，直接降探索深度。第二层在提示词里给**停止判据**——能点名要改的具体内容，或搜索结果约 70% 收敛到同一区域就收手。第三层如果还不够，直接卡**硬预算**，比如「最多 2 次工具调用」。关键是第三层必须配一个**逃生舱口**，比如「哪怕不完全正确也要尽快给答案」——否则模型为了满足正确性会突破你给的预算。

**Q：`reasoning_effort` 和 `verbosity` 有什么区别？**
A：`reasoning_effort` 控制**思考**的深度和调用工具的积极性，默认 medium；`verbosity` 是 GPT-5 新增的，控制**最终答案**的长度，跟思考长度无关。它们正交。Cursor 的最佳实践是把 `verbosity` 全局设 low 保证状态更新简洁，再用提示词单独要求编程工具里用高详略度——因为参数只是整次执行的默认值，模型能响应提示词里的自然语言局部覆盖。

**Q：什么时候用 `minimal` 推理力度？要注意什么？**
A：延迟敏感的场景，以及从 GPT-4.1 迁移过来的用户，这是最合适的升级。注意它**表现随提示词波动比高档位剧烈得多**，所以要补四件事：让它在答案开头用列表简述思路、要求详尽的工具前导语、最大限度消除工具指令歧义并插入坚持度提醒防止提前收工、以及由提示词驱动的显式规划——因为它内部可用于规划的推理 token 变少了。

**Q：工具前导语解决什么问题？一份好的前导语提示词长什么样？**
A：解决长执行链路里用户「不知道智能体在干嘛」的问题，链路越长价值越大。好的写法覆盖四个时间点：调用任何工具前先友好复述用户目标、紧接着给一份结构化计划、执行时按序简明叙述并标记进度、最后给一份**与开头计划明确区分**的完成总结。最后那个「区分」很重要，否则用户无法对照计划和实际。

**Q：为什么说糟糕的提示词对 GPT-5 伤害更大？**
A：因为它遵循指令的精度极高，遇到自相矛盾的指令时会**耗费推理 token 去调和矛盾**，而不是像其他模型那样随便挑一条执行。原文那个医疗排期的例子——「没同意绝不排期」和「不联系患者就先排最早时段」直接打架。修法是解决指令层级冲突：把自动分配改到告知患者之后，再给紧急情况加一条「不查档案」的豁免。所以提示词库要定期审查，官方也提供了提示词优化工具专门找这类问题。

**Q：这篇和 Anthropic 的上下文工程比，思路差在哪？**
A：解的是同一个问题——让模型少做无用探索——但抓手不同。OpenAI 给的是**可调参数加可复制的提示词块**，你拧旋钮就行；Anthropic 讲的是**上下文工程**，从注意力预算和上下文衰减出发，用即时检索、压缩、子智能体这些手段从架构上控制什么进上下文。前者见效快、便于 A/B；后者上限更高但要动系统设计。两家在「智能体必须有自我验证的闭环」这一点上是完全一致的。

**Q：Responses API 值得换吗？**
A：值得，而且有硬数字。它在多次工具调用之间保留推理过程，仅仅换 API 并用 `previous_response_id` 回传之前的推理条目，Tau-Bench Retail 就从 73.9% 涨到 78.2%。原理是模型能回看自己的推理轨迹，省思维链 token，不用每次工具调用后从头重建计划，延迟和性能双改善。ZDR 组织也能用。

## 必须记住的 8 句话

1. 智能体的「放手程度」是一条光谱，GPT-5 被训练成能在任意位置工作——你的活儿是明确指定档位，而不是指望默认值。
2. 收窄探索的三件套：调低 `reasoning_effort` + 写清停止判据（约 70% 收敛）+ 卡硬预算（最多 2 次工具调用）。
3. **限制上下文收集时必须给逃生舱口**，一句「哪怕不完全正确」就够——否则模型会为了正确性突破预算。
4. `reasoning_effort` 管思考深度（默认 medium），`verbosity` 管最终答案长度，两者正交；参数定全局基线，提示词做场景覆盖。
5. 不同工具应该有不同的自主性阈值：支付和删文件要低，搜索和 `grep` 要高。
6. 换到 Responses API 并回传 `previous_response_id`，Tau-Bench Retail 从 73.9% 升到 78.2%。
7. 没有客观检查的开放式任务，用自我反思让模型先造一套 5–7 类别的评分表，不达满分就重来。
8. GPT-5 对矛盾指令特别敏感——它会烧推理 token 去调和冲突，所以清理提示词里的指令层级冲突是收益最高的一次性动作。

## 30 秒口述版

> 这篇讲的是怎么给 GPT-5 设「档位」。核心概念叫智能体的放手程度：GPT-5 能从全权自主到严格受控的任意位置工作，默认偏彻底。要它少探索，就调低 `reasoning_effort`，在提示词里写停止判据——比如搜索结果约 70% 收敛就收手，甚至硬卡「最多 2 次工具调用」；关键是必须留一句「哪怕不完全正确」的逃生舱口，否则它会为了正确性突破预算。要它多自主，就调高推理力度加一段坚持度提示词，明确停止条件、安全边界，并且给不同工具设不同的确认阈值——支付和删文件低，搜索高。参数上还有一个新的 `verbosity` 管最终答案长度，和管思考深度的 `reasoning_effort` 正交；Cursor 的最佳实践是全局设低、只在编程工具里要求高详略度。质量方面用自我反思：让模型先造一套 5 到 7 个类别的评分表，不达满分推倒重来。还有两个高收益动作：换 Responses API 并回传推理条目，Tau-Bench Retail 从 73.9 涨到 78.2；以及清理提示词里的矛盾指令，因为 GPT-5 会认真去调和冲突而不是随便挑一条，糟糕的提示词对它伤害反而更大。最后用元提示让 GPT-5 自己给出最小化的提示词修改建议。对比 Anthropic 的话：OpenAI 给的是可调参数，Anthropic 强调上下文工程和注意力预算，但两家都认同智能体必须有自我验证的闭环。
