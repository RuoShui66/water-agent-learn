## 一句话摘要

数据 Agent 的难点不只是生成 SQL，而是知道“哪张表在业务上真正代表什么”；OpenAI 用表使用记录、人类注释、代码语义、组织知识、记忆和实时查询组成多层上下文，并用权限透传与系统化 eval 维持信任。

## 系统做什么

员工可以从 Slack、Web、IDE、Codex CLI 或内部 ChatGPT 询问开放式数据问题。Agent 负责理解问题、探索数据、执行查询、检查异常结果、调整路径并生成报告。它服务于 OpenAI 内部数据和权限体系，不是对外产品。

## 六层上下文

1. **Table Usage**：schema、表血缘和历史查询，帮助理解常见 join 与使用方式。
2. **Human Annotations**：领域专家补充业务含义、意图和已知陷阱。
3. **Codex Enrichment**：读取生成数据的代码，理解字段如何计算、更新频率、粒度和排除条件。
4. **Institutional Knowledge**：组织中的术语、产品与业务背景。
5. **Memory**：把经过用户确认的纠正保存为个人或全局记忆，并允许编辑。
6. **Runtime Context**：信息缺失或过期时，实时检查仓库、warehouse、Airflow 或 Spark 等系统。

离线管道把多类上下文归一化并生成 embedding；查询时只检索相关部分，而不是扫描数万张表的全部元数据。

## 三条最重要的经验

### Less is More

暴露全部重叠工具会让模型难以选择。合并和限制工具后，路径反而更可靠。工具数量不是能力的同义词。

### Guide the Goal, Not the Path

过度规定每一步会把 Agent 推入不适合当前问题的固定路线。对强推理模型，明确目标、边界和验证标准通常比硬编码完整过程更稳。

### Meaning Lives in Code

Schema 告诉你数据长什么样，历史 SQL 告诉你过去怎么用，但数据真正的生成语义往往只存在于 pipeline 代码。用 Codex 读取代码补全数据目录，是本文最值得借鉴的设计。

## 可靠性与安全

- Agent 继承现有权限，用户只能查询自己本来有权访问的表；
- 查询与原始结果可追踪，回答同时暴露关键假设和执行步骤；
- 系统通过离线 eval、生产反馈与持续监控防止质量漂移；
- 记忆由用户确认和编辑，避免一次误解永久污染全局知识。

## 可直接带走的工程原则

- RAG 不要只索引文档；还要索引代码、血缘、使用记录和人工语义。
- 检索内容按“为什么与当前任务相关”排序，而不只按向量相似度。
- 工具应尽量正交，每个能力只有一个首选入口。
- 查询前继承调用者权限，绝不能让 Agent 使用一个超级账户替所有人查数据。
- 让用户能看见 SQL、数据来源、假设和中间产物，方便验证。
- 记忆写入应有确认、作用域、编辑与删除机制。
